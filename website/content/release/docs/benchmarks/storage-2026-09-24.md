# Linode volume and R2: one burst, different access patterns

Measured September 24, 2026. This is a bounded experiment, not a cloud-wide
performance guarantee or an end-to-end model-loading benchmark.

## Environment and method

One Chicago Linode CPU burst (`us-ord`, `g6-standard-2`, 2 shared vCPUs,
4 GiB RAM), one new 10 GB block volume, and a private R2 Standard bucket
reporting location `ENAM`. The same pod ran all tests, with a 1 GiB memory limit.
Boot, network bootstrap, package installation, and volume attachment are excluded.

- Volume: ext4, 1 MiB blocks, direct I/O, queue depth 16, fio 3.33.
  Three 2 GiB reads and writes; reported writes include final sync and process
  overhead, while reads use fio's I/O throughput.
- R2: direct S3 HTTPS, not a CDN, filesystem mount, or Yscale cache initializer.
  Three single-object 2 GiB GET/PUT samples and three batches of eight parallel
  128 MiB objects. Single-object GET measurements also compute SHA-256.
- Synthetic payload. Full-object downloads were checksum-verified. No actual
  inference framework or model was loaded, and R2 service-side cache state was
  not controlled.

## Throughput

MiB/s, median of three samples, with observed range in parentheses:

| Path | Read / GET | Write / PUT |
|---|---:|---:|
| Volume, direct I/O, QD 16 | 266.9 (228.9–306.6) | 167.6 (149.0–179.1) |
| R2, one 2 GiB stream | 48.9 (34.5–69.4) | 36.1 (28.1–45.5) |
| R2, eight parallel 128 MiB objects | 180.2 (113.6–180.7) | 127.6 (117.0–152.6) |

These tests have different concurrency and durability semantics. They are not
a universal storage ranking. Volume 4 KiB random reads at queue depth 1 measured
51.6 IOPS with mean latency 19.32 ms; a high sequential rate does not imply fast
small random reads.

## Whole-file results

For the same 2 GiB payload:

- Buffered volume scan and SHA-256 after file-scoped cache advice: 63.5 seconds.
- Repeated buffered volume scan and SHA-256: 31.6 seconds.
- R2 download to root disk, SHA-256, and final sync: 35.6 seconds.

The file was larger than the pod's memory limit, so the repeat was not a fully
RAM-cached read. The R2 test includes a destination write; volume scans do not.
Pre-seeding avoids another object download but does not eliminate application
reads. Test your workload's actual access pattern before choosing a storage path.

## Product boundary and lifecycle

The volume write test was a scratch-storage benchmark. Yscale's shipped Linode
`modelVolume` path is read-only; generic writable durable volumes are not implied.
The R2 timings do not measure `spec.storage.cache` startup end to end.

One VM was reused for the full suite and then removed. Temporary VM, volume,
bucket/objects, and Kubernetes benchmark resources were cleaned up and verified.
Private resource identifiers and operator receipts are not part of this public
summary. See the [storage guide](../storage.md) for supported application paths.
